OPTIMIZATION OPPORTUNITIES (RANKED)
═══════════════════════════════════════════════════════════════

1. **Function::Args vector** - 14.7% of parse time
   Problem: Each function call allocates std::vector<string_view> for Args
   Solution: Use small-buffer optimization or store indices instead
   Impact: High - most frequent allocation source

2. **Hash table bucket allocations** - ~7.9% of parse time  
   Problem: MetaSection/PatternSection use std::unordered_map
           which reallocates buckets during growth
   Solution: Pre-size hash tables or use flat_map/vector
   Impact: Medium - affects rules with many meta/pattern entries

3. **AST node allocations** - ALREADY OPTIMIZED ✓
   Problem: Was allocating nodes via shared_ptr
   Solution: Arena allocation with std::deque
   Status: Complete, minimal remaining overhead

═══════════════════════════════════════════════════════════════
WHY ARENA ALLOCATION SHOWED ONLY 0.2% IMPROVEMENT
═══════════════════════════════════════════════════════════════

The arena allocation optimization successfully eliminated AST node
allocations, but this represented only ~5 samples (2.8%) of the 
total 177 samples. The real allocation hotspots are:

1. Function::Args vectors: 26 samples (14.7%)
2. Hash table growth: 14-20 samples (7.9-11.3%)

Arena allocation targeted the wrong bottleneck. While it improved
code quality (better memory management, bulk deallocation), the
performance impact was minimal because AST nodes were a small
fraction of total allocations.

The profiling reveals that ~38/177 samples (21.5%) are spent on
memory management, with Function::Args being the dominant source.

NEXT STEPS
